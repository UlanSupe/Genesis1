# TraceForge — Evidence-First Financial Audit Gym

TraceForge — автономная, воспроизводимая **RL-среда** для исследования и потенциального дообучения
ИИ-агентов, выполняющих финансовый аудит. Это не бухгалтерский SaaS и не платёжное приложение:
среда генерирует синтетические компании со связной историей операций, внедряет в неё проверяемые
ошибки, даёт агенту ограниченный набор инструментов расследования и оценивает ответ строгим
one-to-one сопоставлением и официальной функцией награды.

> Мы создаём **среду**, а не доказываем, что какая-либо модель стала умнее. В репозитории нет
> результатов обучения моделей; все приведённые числа получены запуском `verify`/`evaluate`/`benchmark`/`demo`.

## Зачем это нужно

Аудит — это поиск конкретных расхождений: платёж, отнесённый не на тот счёт; счёт, проведённый дважды; курс не за ту дату; операция
в чужом отчётном периоде. Реальные данные закрыты и не имеют «правильного ответа», а ложное обвинение стоит почти так же дорого, как
пропущенная ошибка. TraceForge даёт **проверяемый стенд**: синтетическая компания со связной историей, внедрённые ошибки с известной
причиной, суммой и доказательствами, ограниченные инструменты расследования и награда, которая штрафует и пропуски, и ложные тревоги.
Законные «двойники» ошибок (возвраты, повторяющиеся суммы, разделённые платежи, платежи у границы периода из другого часового пояса)
есть в каждом эпизоде.

## Основные технические возможности

* генератор синтетических компаний (целочисленные minor units, `Decimal`-курсы, несколько валют и часовых поясов, детерминированный по seed);
* 4 типа ошибок + 2 compound-сценария, уровни сложности `easy / medium / hard / compound`, у каждой ошибки причина, сумма, доказательства и подробное объяснение;
* независимый валидатор: каждая ошибка проверяема по публичным данным, чистые компании чисты, доказательства достаточны;
* среда `reset/step` в стиле Gymnasium, 5 инструментов, лимиты 100 шагов / 50 строк, безопасный калькулятор (AST + `Decimal`);
* строгое one-to-one сопоставление (максимальное паросочетание) и официальная награда `clip(2·F1 − 1 − 0.002·steps, −1, 1)`;
* изоляция: эталон только в процессе оценщика, агент — отдельный процесс, сканер утечек на каждом сообщении;
* 4 baseline-политики (random, reconciliation, mark-all, oracle только на стороне оценщика), запись траекторий, метаморфическая проверка (24 пары);
* **демонстрация одной командой** с HTML-отчётом по реальным результатам; только стандартная библиотека, без сети, GPU, LLM и платных API.

Измерено: эпизод на 12 ошибок и 150 счетов генерируется и проходит полный прогон за ~0,3 с при пике памяти ~7 МБ (tracemalloc);
генерация эпизода на ~2000 проводок — ~0,9 с (см. `FINAL_ENGINEERING_REPORT.md`).

## Быстрый старт

```bash
pip install -e .                 # или без установки: PYTHONPATH=src (Windows: $env:PYTHONPATH="src")
pip install -r requirements-dev.txt   # pytest==9.1.1, только для тестов

python -m traceforge demo        # ДЕМОНСТРАЦИЯ: фиксированный seed, расследование, оценка, benchmark, reports/demo_report.html
python -m traceforge benchmark   # все 4 политики на одинаковых эпизодах -> reports/benchmark.json/.csv (+ по уровням сложности)
python -m pytest                 # 1324 теста
python -m traceforge verify      # тесты + матрица SPEC_COMPLIANCE.md + аудит + метаморфика + benchmark
python -m traceforge generate    # datasets/train (10) и datasets/dev (10)
```

`demo` работает без цвета (`--no-color` или переменная `NO_COLOR`), печатает только ASCII и пишет `reports/demo_report.html`
(самодостаточная страница с SVG-графиками по реальным данным), `reports/demo_result.json` и траекторию агента
`trajectories/demo_seed7.jsonl`. Эталон в обычном запуске не показывается (`--instructor` — отдельный явный блок).
Для жюри: [JUDGE_SUMMARY.md](JUDGE_SUMMARY.md) (краткое описание и результаты), [FINAL_AUDIT.md](FINAL_AUDIT.md) (аудит требований, безопасности и воспроизводимости),
`FINAL_BENCHMARK.json/.csv` (реальный benchmark, 52 эпизода x 4 политики), `requirements.txt`. Проверка в чистом окружении: `bash tools/clean_env_check.sh`.
Сценарий презентации на 3 минуты — [DEMO_SCRIPT.md](DEMO_SCRIPT.md), устройство системы — [ARCHITECTURE.md](ARCHITECTURE.md) (диаграммы Mermaid).

Проверено на Python 3.12.0 (Windows 11). Проект требует `>=3.11` и не использует возможностей
только 3.12, но на 3.11 в этой среде он не запускался.

| `python -m traceforge audit [--skip-performance]` | Автоматический аудит: валидатор на всех пресетах/типах/сценариях, AST-скан архитектуры (нет `eval/exec`, глобального `random`, сети, сторонних зависимостей), проверка «структурных подсказок» генератора, воспроизводимость между процессами (`PYTHONHASHSEED`), фаззинг среды и калькулятора, замеры производительности → `reports/audit_report.json`, `reports/performance.json` |
| `python -m traceforge benchmark [--suite dev\|train\|presets\|all] [--policy all] [--isolated]` | Все политики на одинаковых эпизодах; precision, recall, F1, reward, inspection steps, runtime, число выводов → `reports/benchmark.json`, `benchmark.csv`, `benchmark_summary.csv` |

Примеры: `examples/gym_loop.py` (reset/step), `examples/run_custom_agent.py` (внешний агент по протоколу).

## Формат данных

Эпизод хранится в двух физически разных папках:

```
episode/public/   manifest.json  ledger.csv  invoices.jsonl  payments.jsonl  fx.csv  policy.json
episode/private/  truth.json  provenance.json  clean_baseline.json
```

* Деньги — только целые minor units; курсы — десятичные строки (8 знаков); время — ISO-8601 со смещением;
  отсутствующие ссылки — `null` (в CSV — литерал `null`).
* `manifest.json`: `schema_version, episode_id, base_currency, period_start, period_end, timezone,
  record_count, document_count, rounding_rules`. `period_end` — **исключающая** граница.
* `ledger.csv`: `row_id, timestamp, account, debit_minor, credit_minor, currency, entity_id, invoice_id, payment_id`.
  Суммы проводок всегда в **базовой валюте**; колонка `currency` — валюта исходного документа.
* `invoices.jsonl`: `doc_id, invoice_id, entity_id, issued_at, due_at, currency, total_minor, line_items`.
* `payments.jsonl`: `doc_id, payment_id, timestamp, currency, amount_minor, invoice_refs`, где
  `invoice_refs = [{"invoice_id", "allocated_minor"}]`. Отрицательный `amount_minor` — возврат.
  Несопоставленный остаток платежа (`amount − Σallocated`) законно проводится на счёт 2300.
* `fx.csv`: `date, source_currency, target_currency, rate` (1 ед. источника = `rate` ед. базовой валюты).
  Идентификатор записи для `get_record("fx", …)` и доказательств: `FX-{date}-{SRC}-{TGT}`.
* `policy.json`: границы периода, правило признания, правило даты курса (календарная дата документа в
  часовом поясе компании), округление `ROUND_HALF_UP` по строке проводки, допуск суммы, план счетов и
  **соглашения о полях выводов** для каждого типа ошибки (`finding_conventions`).
* `truth.json`: `issue_id, type, affected_ids, expected_amount_minor, currency, allowed_evidence_sets` плюс
  `root_cause` (код причины, напр. `allocation_applied_to_wrong_invoice`) и `explanation` (подробное описание: что произошло,
  по каким записям это видно, как получена сумма). Оценщик эти два поля **не использует**, агент их не видит.
  `provenance.json`: история генерации, мутации (`mutation_id, issue_id, issue_type, source_rows,
  modified_rows, causal_description, changed_amount_minor, document_ids, available_evidence`), сценарии,
  отчёт валидации. `clean_baseline.json`: журнал до внедрения ошибок.

Проводки: счёт-фактура `Dr 1200 / Cr 4000`; платёж `Dr 1000` (сумма строк) `/ Cr 1200` по каждой ссылке
`/ Cr 2300` на остаток; возврат — зеркально. **Единица журнала** — `payment_id`, иначе `invoice_id`.

Идентификаторы строк `ROW-…` присваиваются **после** внедрения ошибок и финальной сортировки, поэтому
номер строки не выдаёт, какая запись внедрена.

## Четыре типа ошибок (независимые движки)

Каждый тип настраивается отдельно (`issue_counts`, `mutation_weights`); один документ мутируется не более одного раза; все журналы остаются сбалансированными.

| Тип | Что внедряется | `affected_ids` | Сумма |
|---|---|---|---|
| `duplicate` | Журнал документа проведён дважды | `[invoice_id\|payment_id]` | сумма якорной строки повтора |
| `allocation` | Платёж распределён неверно: `unallocated` (строка ушла на 2300), `partial` (часть на 2300), `wrong_invoice` (другой счёт) | `[payment_id]` + все счета с расхождением | суммарный недобор |
| `fx` | Неверный курс (`wrong_rate`) или курс другой даты (`wrong_date`) | `[invoice_id\|payment_id]` | \|проведено − верно\| по якорной строке |
| `cutoff` | Журнал отнесён к другому отчётному периоду, чем документ | все `row_id` такого журнала с расхождением периода | большая из сумм дебета/кредита этих строк |

Законные ситуации, **не** являющиеся ошибками (есть в каждом эпизоде, в чистых — тоже): повторяющиеся суммы
у одного контрагента, одинаковые суммы у разных, возвраты, частичные и разделённые платежи, переплата
с остатком на 2300, корректный пересчёт валют (в т.ч. JPY — 0 знаков, KWD — 3), операции в пределах часа
от границы периода от контрагента с другим часовым поясом (локальная дата отличается от даты компании).

## Compound-сценарии

Оба дают **две отдельные** эталонные ошибки со своими доказательствами и суммами, на разных журналах
с общей «историей»:

1. `cross_border_partial` — иностранный счёт погашен двумя частичными платежами; один платёж распределён
   неверно (`allocation`), другой пересчитан по курсу не той даты (`fx`).
2. `period_end_duplicate` — два «двойника» счёта у одного контрагента (одинаковые строки и сумма) в конце периода:
   журнал одного проведён дважды (`duplicate`), журнал другого отнесён в следующий период (`cutoff`).

## Валидация и provenance

### Уровни сложности (определяют, какие варианты ошибок встречаются и насколько они тонкие)

| Уровень | Идея | duplicate | allocation | fx | cutoff |
|---|---|---|---|---|---|
| **easy** | ясные аномалии, прямые доказательства | повтор обычного документа | `unallocated` | `wrong_rate` на 3–5 % | проводка ≥ суток за границей периода |
| **medium** | нужна перекрёстная сверка нескольких записей | любой документ | `unallocated`, `partial` | `wrong_rate` 1,5–3 % и `wrong_date` (нужна таблица курсов) | сдвиг 4–24 ч |
| **hard** | косвенные доказательства, правдоподобные двойники | повтор документа, у которого есть законный двойник | `partial`, `wrong_invoice` (сравнить два счёта) | `wrong_rate` 0,5–1,5 %, `wrong_date` соседних дней | сдвиг 15 мин – 3 ч |
| **compound** | два взаимодействующих сценария + hard-данные | — | — | — | — |

Соглашения о доказательствах для `allocation` включают `doc_id` всех счетов из `affected_ids` (перекрёстная ссылка). Ни один уровень
не скрывает информацию: валидатор доказывает разрешимость каждого эпизода по публичным данным. Рост сложности для агента — это объём
данных, число связей (разделённые/частичные платежи) и тонкость различий, а не неразрешимость.

Сложность задаётся **числом взаимосвязей** (разделённые/частичные/двухчастичные платежи, валюты, контрагенты, отвлекающие случаи,
число ошибок), а не скрытием данных: `easy / medium / hard / compound` (`config.PRESETS`); все эпизоды остаются полностью
разрешимыми по публичным данным. Размер (счета, контрагенты), масштаб сумм и объём отвлекающих случаев варьируются по эпизодам.
Законные отвлекающие случаи (в каждом эпизоде): повторяющиеся суммы, одинаковые суммы у разных контрагентов, **серии одинаковых
счетов (подписка)**, возвраты, переплаты с остатком на 2300, **разделённые платежи**, граничные по времени платежи из других часовых
поясов. Отвлекающие документы **не иммунны** к ошибкам (иначе «выглядит как decoy» было бы бесплатной подсказкой «безопасно»).

`generator/validation.py` содержит **независимую** реализацию правил проводок: она выводит все расхождения
только из публичных данных и требует точного совпадения с `truth.json` (тип, ids, сумма, валюта). Проверки истины (все автоматические, на каждом сгенерированном эпизоде): аномалия реально присутствует в данных; все `affected_ids`
существуют; все `evidence_ids` существуют и доступны инструментами; **каждый допустимый набор доказательств сам по себе восстанавливает ровно
свой вывод** (запуск независимого детектора только на документах из доказательства); чистые компании не содержат аномалий; нетронутые
decoy-журналы совпадают с независимым ожидаемым проведением; **итоги по счетам и за период меняются только на сумму заявленных аномалий**.
Дополнительно: **независимая пересборка чистого журнала** из документов+курсов+политики (должна совпасть с `clean_baseline`),
**повторное применение манифестов мутаций** к baseline (результат обязан в точности равняться публичному журналу, т.е. нет ни одного
незаявленного расхождения), ссылочная целостность, непересекающиеся идентификаторы, остатки по счетам в диапазоне [0, сумма], причинная
связность манифестов. Любая проверка, которую нельзя вычислить на испорченных данных, **падает с причиной**, а не бросает исключение.
Также проверяются:
согласованность и баланс чистой базы, изменение ровно нужных документов, сумма > допуска, публичность и
доступность всех evidence ids, отсутствие приватных маркеров в public, лимиты размера. Неудачная генерация
детерминированно повторяется с производным потоком случайных чисел (до 6 попыток).

## Контракт среды

```python
env = AuditEnv(mode="train" | "eval")
obs, info = env.reset(seed, config)            # config: поля GeneratorConfig или {"episode_dir": "..."}
obs, reward, terminated, truncated, info = env.step(action)
```

Действия (JSON-словари): `list_records{table,cursor,limit}`, `get_record{table,id}`, `get_document{doc_id}`,
`calculator{expression}`, `submit{findings}`; таблицы: `ledger, invoices, payments, fx`.

* максимум **100** действий включая `submit`; страница ≤ **50** записей (`limit>50` — ошибка, шаг тратится);
  пагинация стабильна (курсор `c<offset>`, порядок неизменен в эпизоде);
* неизвестный id, неверное действие, неверный курсор — расходуют шаг; ошибки фиксированного текста,
  не повторяют ввод и не раскрывают эталон; нет shell/SQL/файлов/сети/произвольного кода;
* `calculator` — AST-белый список + `Decimal` (числа, `+ - * / // % **` с целой степенью ≤12, скобки,
  `round/abs/min/max`), без `eval/exec`, без имён и атрибутов, с лимитами длины/узлов/порядка чисел;
* наблюдение содержит только `task, manifest, policy, last_result, error, steps_remaining`;
* 100 шагов без `submit` → `truncated=true`, ответ пустой (оценивается как пустой, `inspection_steps=100`);
  `submit` → `terminated=true`; исследовательские шаги дают `reward=0`;
* `train`: терминальная награда возвращается агенту; `eval`: агент получает `0.0`, а полную оценку
  (`env.result`) читает только внешний runner после завершения.

## Контракт submit

```json
{"episode_id": "...", "findings": [
  {"type": "fx", "affected_ids": ["PAY-0007"], "claimed_amount_minor": 448, "currency": "EUR",
   "evidence_ids": ["DOC-0099", "ROW-00201", "FX-2026-01-30-CHF-EUR"], "explanation": "..."}]}
```

Лимиты: ≤30 выводов, ≤10 `evidence_ids`, ≤20 `affected_ids`, `explanation` ≤1000 символов; `claimed_amount_minor` —
целое (не bool/float). Неверная структура → завершение с `reward = −1` и запись в внутренний журнал оценщика
(агенту детали не сообщаются). `action.findings` может быть и просто списком — среда обернёт его сама.
Текст `explanation` **не оценивается**.

## Алгоритм сопоставления (matcher)

Прогноз — кандидат на TP для эталонной ошибки, только если выполнены **все** условия:

1. `type.strip().lower()` равен типу ошибки;
2. `affected_ids` совпадают как **множества** (после `strip`, пустые и повторы отбрасываются);
3. `|claimed − expected| ≤ 1` minor unit (опубликованный допуск);
4. `currency.strip().upper()` совпадает;
5. `evidence_ids` содержат (как надмножество) хотя бы один полный набор из `allowed_evidence_sets`.
   Лишние и неизвестные id безвредны, но недостаточны.

Каждый прогноз — максимум одной ошибке, каждая ошибка — максимум один раз. Несопоставленные прогнозы = FP,
пропущенные ошибки = FN. Используется **максимальное двудольное паросочетание** (пути Куна), а не жадный
алгоритм. Правило разрешения неоднозначности: прогнозы обходятся в каноническом порядке (тип, ids, сумма, валюта,
доказательства, индекс), каждый перебирает совместимые эталоны по возрастанию `issue_id`. Эквивалентные прогнозы
взаимозаменяемы, поэтому TP/FP/FN не зависят от порядка в ответе (проверено тестами с перестановками).

## Награда

```
F1 = 2·TP / (2·TP + FP + FN)          # F1 = 1, если эталон пуст и прогнозов нет; F1 = 0, если эталон пуст, а прогнозы есть
reward = clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)
```

`inspection_steps` — число действий до `submit` (все неверные — тоже). Считается точными дробями (`fractions`), чтобы
одинаковые входы давали побитово одинаковую награду. Метрики: TP, FP, FN, precision, recall, F1, reward,
inspection_steps, elapsed_time (соглашение для пустых множеств — в `evaluation/metrics.py`).

## Изоляция

* **PUBLIC AGENT VIEW** — только JSON-наблюдения. **PRIVATE EVALUATOR VIEW** — `AuditEnv` (хранит `Evaluator`
  с эталоном) и runner. `AuditEnv` — объект стороны оценщика; агенту его не передают.
* Агент запускается **отдельным процессом** (`--isolated`): очищенное окружение, пустой рабочий каталог,
  общение только JSON-строками (`runner/agent_protocol.py`). Агент-процесс не импортирует генератор и оценщик.
  Тест запускает «враждебного» агента, который обшаривает `gc`, `sys.modules`, окружение и каталог, — приватных данных нет.
* Oracle доступен только на стороне оценщика, не входит в `policies.REGISTRY`, и `agent_worker` отказывается его загружать.
* Защита runner'а от враждебного агента: ограничение длины сообщения (агент убивается, память evaluator не растёт), stderr читается в
  ограниченный буфер, таймаут вызова и общий дедлайн эпизода, на POSIX — `RLIMIT_AS/CPU`. Кастомным агентам не передаётся `PYTHONPATH`
  (путь проекта и каталогов `private/` им неизвестен).
* Защита от утечек: `LeakGuard` (`assert_no_leak`) сканирует каждое наблюдение/`info`/траекторию на issue-id и
  служебные маркеры; тесты проверяют `info`, ошибки, исключения, траектории; seed не попадает ни в `info`, ни в траектории.

## Baseline-политики

| Политика | Сторона | Идея |
|---|---|---|
| `random` | агент | Случайные действия с фиксированным seed (`random.Random`), затем 0–3 случайных вывода |
| `reconciliation` | агент | Читает все таблицы, ищет повторные проводки, пересчитывает курс, сверяет распределение платежей, сравнивает периоды |
| `mark_all` | агент | Обвиняет самые «подозрительные» документы по всем типам (до 30) — проверка защиты от FP |
| `oracle` | **оценщик** | Строит выводы из `truth.json`; проверяет, что награда 1.0 достижима |

Измеренные результаты (режим eval, `python -m traceforge benchmark --seeds 8`, 208 прогонов; полные таблицы, в т.ч. по уровням сложности, — в `FINAL_ENGINEERING_REPORT.md` и `reports/benchmark*.csv`): на `dev` oracle F1 = 1.000 / reward = 1.000; reconciliation F1 = 1.000 / reward = 0.964 (18 шагов); mark_all F1 = 0.000 / reward = -1.000; random F1 = 0.000 / reward = -1.000. По уровням reconciliation держит F1 = 1.000, но тратит больше шагов (easy 12.4, hard 24.1), поэтому reward падает с 0.975 до 0.952.

## Метаморфическое тестирование

`generator/transformations.py` меняет id документов/проводок/контрагентов (с обновлением всех ссылок, truth,
provenance, baseline), переставляет порядок строк и документов, переименовывает нейтральные описания.
Проверяется: Oracle и `reconciliation` получают одинаковые F1, reward и число шагов на оригинале и
преобразовании; сохранение экономического смысла; повторная валидация. Результаты 24 пар (структурная проверка связей, 10 негативных контролей) пишутся в
`reports/transformation_report.json`.

## Ограничения

* Синтетическая предметная область: цикл «счёт → платёж» дебиторской задолженности; ровно 4 типа ошибок;
  валютные курсы — ежедневные, включая выходные; часовые пояса — фиксированные смещения без DST.
* Эталон однозначен только при следовании опубликованным соглашениям (`policy.finding_conventions`).
* Простая политика `reconciliation` решает эпизоды почти идеально, потому что ошибки по построению проверяемы по
  публичным данным (это и есть цель валидатора). Сложность для LLM-агентов определяется бюджетом шагов, объёмом данных и
  отвлекающими случаями; для усложнения увеличьте `difficulty`, `n_invoices`, число валют. Никаких выводов о качестве моделей мы не делаем.
* Изоляция — на уровне процессов. Она не защищает от агента с доступом к файловой системе ОС (может прочитать
  `private/` сохранённых эпизодов); для враждебных агентов запускайте их в контейнере/под другим пользователем и
  используйте эпизоды, сгенерированные в памяти. Знание `seed` + кода позволяет восстановить эталон — храните eval-seed в секрете.
* В `train` режиме награда возвращается агенту; в `eval` — скрыта, но только если runner сам не передаёт её агенту.
* Проверено на Windows 11 / Python 3.12.0; Python 3.11 заявлен, но не запускался.
